## What works

### CLI

```bash
pnpm -r build
node packages/cli/dist/bin/wcag-toolkit.js audit <path>
node packages/cli/dist/bin/wcag-toolkit.js audit <path> --json
node packages/cli/dist/bin/wcag-toolkit.js audit <path> --top 20
```

Exits non-zero when there is at least one Critical or Serious finding, so it
plugs into CI without extra wiring.

### Packages

- `@sdet-wcag-toolkit/core` - types, WCAG 2.2 A/AA catalog (55 SCs),
  severity weights with A-F grading, priority scoring.
- `@sdet-wcag-toolkit/static-analyzer` - orchestrator + 4 analyzers:
  - `semanticAnalyzer` - title, `html[lang]`, `main`, heading order, lists,
    tables, image `alt`.
  - `ariaAnalyzer` - valid roles, required attrs, id-ref integrity,
    `aria-hidden` on focusables, redundant roles.
  - `keyboardAnalyzer` - positive tabindex, unfocusable interactive roles,
    click without keyboard affordance.
  - `contrastAnalyzer` - CSS rules and inline styles where both
    foreground/background are statically resolvable.
- `@sdet-wcag-toolkit/cli` - `audit` command with console + JSON output.

### Claude Code integration

- Agents: `wcag-lead`, `semantic-structure-agent`, `aria-patterns-agent`,
  `keyboard-interaction-agent`, `color-contrast-static-agent`.
- Skill: `wcag-static-analyze`.
- Command: `/wcag:audit:static <path>`.

### Demo fixture

`examples/demo-site/` - a tiny static site with 15 intentional violations
covering every rule in every analyzer. Integration test in
`packages/cli/src/integration.test.ts` asserts the audit pipeline still
catches all rule categories.

## Known limitations

- **HTML/CSS only.** JSX/TSX files are loaded but not analyzed in v0.1.
  Tracking issue: add AST-based JSX scan in v0.2.
- **No line numbers in HTML findings.** `cheerio` default parsing does not
  track source locations. CSS findings report line numbers via `postcss`.
- **No forms analyzer yet.** Forms coverage lands in Sprint 2 per plan.
- **Static contrast is deliberately narrow.** Anything involving `var(--…)`,
  `:hover`, or layered backgrounds is out of scope. Dynamic axe-core will
  fill that gap in v0.2.
- **No focus-trap detection.** Requires runtime; deferred to dynamic tester.

## Pivot mid-sprint: Model A → Model C

When I got to Part E (Claude agents), I wrote them as thin wrappers over
the TypeScript analyzer - each specialist was a four-line markdown file
that said "call `semanticAnalyzer.analyze()` and return the result."
I tagged v0.1.0 on 20 December, cloned into a real React project a few
days later, and ran the audit.

Nothing interesting came back. The TS analyzer only understands HTML
and CSS; in the React `src/` it had nothing to say. The agents "worked"
in the sense that the orchestration fired, but they had no independent
intelligence.

That's when the gap surfaced: what actually makes this tool different
from axe-core or the Anthropic `/design` plugin? Deterministic rules on
built output? Everybody does that. The only defensible moat is **Claude
agents reading framework source - JSX, Vue SFCs, Angular templates -
and reasoning about WCAG issues the way a senior reviewer does**. Not
pattern matching; understanding.

So I pivoted over the holiday week. Kept the TS analyzer as the
deterministic CI-path for HTML/CSS and built output (that's real value
too - zero tokens, zero LLM calls). Rewrote the four specialists to
actually read source via `Read` + `Grep` + `Glob`, each one
framework-aware across React / Vue / Angular / Svelte / Astro, emitting
WcagFinding JSON directly. Added `/wcag:init` so other projects can
adopt it without cloning. Rebuilt the demo fixture as
`examples/react-basic/` to showcase both paths side by side.

Tagged v0.1.1 on 10 January as the "pivot release."

### What I'd do differently

Start with Model C. I spent three weeks building the TS analyzer
because the plan said so, when a smaller deterministic core plus
intelligent agents was always the right shape. The plan I wrote on
day one assumed the agents would need something to wrap - because
that's how I'd have done it in a pure-deterministic world. It took
shipping v0.1.0 and running it on a real project to see the shape
was upside-down.

### Lessons for v0.2

1. **Decide the moat first, then choose deterministic vs AI for each
   slice.** Not the other way around.
2. **AI agents are not just LLM calls.** They have tool access and can
   read source. Use that - don't reduce them to wrappers.
3. **Ship early, run it on a real target, then iterate.** v0.1.0 looked
   fine in isolation; it only failed when confronted with a React `src/`.
   Real usage catches design flaws faster than any amount of planning.
4. **Hybrid is underrated.** The deterministic path is still valuable
   for CI; the AI path is the differentiator. Having both is the story.

mid-sprint design pivots, not a tool launch post.
